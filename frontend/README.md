# Event Check-in frontend

React JavaScript app with manual ticket lookup, explicit check-in confirmation,
webcam QR scanning using @zxing/browser, and an Admin Dashboard with printable
ticket QR codes generated by qrcode.react.

See the [root README](../README.md) for setup, REST examples, design decisions,
current demo state, and the five-minute presentation outline. The database now
has **15 tickets, 2 checked in, and 2 logs**. EVT-STANDARD-001 (QR) and EVT-VIP-001
(MANUAL) were checked in during the user-confirmed physical walkthrough. Preserve
these records; use another unchecked reference for future success demonstrations.

## Run locally (Windows PowerShell)

Start two VS Code terminals at the Event-Checkin-System workspace root.

Terminal 1:

```powershell
cd backend
npm.cmd install
npm.cmd run start:dev
```

Terminal 2:

```powershell
cd frontend
npm.cmd install
npm.cmd run dev
```

Open **http://127.0.0.1:5173/** (http://localhost:5173/ also works).
Stop servers with Ctrl+C. Do not start a second instance on the same port.
The existing demo database is used by the normal development servers. Finding a
ticket does not change it; confirming a ticket updates it and adds its log.
Do not reseed or reset tickets to undo check-ins.

## Frontend/backend connection

The frontend uses relative `/api` URLs. Vite forwards only `/api` requests to
http://127.0.0.1:3000 during development. This avoids browser cross-origin
requests and requires no backend CORS changes. The proxy is configured in
`vite.config.js`; there is no deployed API URL in browser code. Vite uses port
5173 with strictPort so an occupied port produces an understandable startup error.

`npm.cmd run build` builds static assets. The development proxy does not become
part of the deployed assets; a future deployment must provide its own /api
reverse proxy. Use the dev server for this local walkthrough.

## Manual workflow

1. Enter an exact ticket reference, for example EVT-VIP-002, then select Find ticket.
   Manual entry trims accidental surrounding whitespace; matching is case-sensitive.
2. Review reference, ticket type, current status, and any existing check-in time.
3. If unchecked, select Confirm check-in. The POST uses method MANUAL. Confirmation
   is disabled while the request is pending and synchronously guarded against
   repeat clicks. No POST occurs during lookup.
4. Success shows type and the returned timestamp, formatted in the browser's local
   time zone. Next ticket clears the result and returns keyboard focus to entry.

## Camera workflow and manual verification

Camera access needs localhost or HTTPS and browser/OS camera permission. An HTTP
LAN address opened on a phone usually cannot use the camera; use the local machine
or a properly configured HTTPS development connection. No camera starts on load.

1. In Chrome or Edge, open http://127.0.0.1:5173/ with both servers running.
2. Select Scan QR code and allow camera access. Confirm that a live preview appears.
3. Present a QR code whose entire content is ONLY a valid ticket reference
   (for example EVT-STANDARD-002 if still unused). Use Admin Dashboard > View QR to display or
   print that ticket first. A URL or JSON object is not the expected QR payload.
4. Confirm that scanning stops, the camera indicator turns off, the ticket details
   appear once, and the entry method says QR scan. Lookup alone must not check in.
5. Select Confirm check-in only when ready to change that demo ticket. Check that
   success displays its type and check-in time. The POST must contain method QR.
6. Scan/find that same ticket again: Already checked in should appear with no
   confirmation button. A server-side duplicate race shows the 409 message too.
7. Start scanning again, select Stop Camera, and verify the camera indicator turns
   off. Repeat while starting the camera; navigate away or switch tabs and confirm
   the camera stops. Returning to the tab should require pressing Scan QR code again.
8. Block camera permission and retry: a permission-denied message should appear.
   Disconnect/disable cameras and retry: a no-camera message should appear.
   In both cases, use Find ticket to confirm manual entry still works.
9. Test a nonexistent reference: Ticket not found. Submit an empty reference:
   Invalid input. Stop the backend and find a ticket: Backend unavailable. Restart
   the backend before retrying. No check-in is performed by these error checks.

One decoded result is accepted per camera session. A synchronous guard rejects
repeated decoder callbacks. Camera tracks and decoder controls are released after
a decode, Stop Camera, component cleanup, navigation, and switching away. A stream
that arrives after Stop Camera is also stopped. A QR lookup always needs a separate
confirmation and uses the same backend endpoint as manual check-in.

## Automated verification

```powershell
npm.cmd run build
npm.cmd run test:e2e
```

The browser tests require backend dependencies and locally installed Google Chrome.
The test command builds the backend, creates a uniquely named temporary SQLite
file, seeds that file only, and serves the actual frontend through Vite with its
proxy pointed at the temporary Nest server. Tests run in headless Chrome. Both
test servers and the temporary database are removed afterward. Demo ticket/log
rows are compared before and after and must remain unchanged.

Tests cover actual manual lookup/check-in, duplicate-click suppression, a real
409 race, actual unknown-ticket 404, simulated HTTP 400 and unavailable-network
messages, keyboard entry, mobile/desktop overflow, simulated QR callbacks, denied
and missing cameras, Stop Camera, navigation, and a late camera stream.

**Camera lifecycle tests simulate media access and decoder callbacks.** Separate
image tests use the real decoder for all 15 rendered QR codes. The user also
confirmed a physical webcam scan and QR check-in during STEP 8; that manual
evidence is separate from automated results. A test-only Vite plugin substitutes
the webcam reader exclusively on the isolated test server; normal development
and builds use the real @zxing/browser package.

Git-ignored results are in `test-results/`: `browser-results.json`,
`database-verification.json`, and desktop/mobile screenshots. The database evidence
records the exact temporary database path, checked-in test references, logs, real
proxied HTTP statuses, and the unchanged demo totals.
The saved zero-check-in demo snapshot predates the physical walkthrough; the
current database legitimately has two check-ins. The documentation review
preserved existing artifacts rather than replacing them with new runs.

References: [ZXing browser API](https://github.com/zxing-js/browser) and
[Vite server proxy](https://vite.dev/config/server-options#server-proxy).

## Admin Dashboard and ticket QR codes (Step 7)

Use Check-in and Admin Dashboard in the top navigation. Switching away from
Check-in unmounts the scanner and releases camera resources. Each dashboard entry
fetches the existing admin ticket and summary APIs again. Refresh fetches both
again without reloading the browser. Counts come from the backend; there is no
local counter that pretends a check-in succeeded. Refresh is disabled while
loading. Failed requests hide stale results and provide a retry message.

The dashboard shows overall totals, checked-in counts for all three types, and a
reference-sorted table with status and local check-in time. The table scrolls
horizontally on mobile. Empty data, loading, and backend errors have explicit
states. This is an **unauthenticated local MVP**; the admin screen and backend
admin endpoints are not access-controlled. There is no login page.

Select View QR on any row, whether checked in or not. A keyboard-accessible
modal shows the reference, type, status, and a black-on-white QR with a four-module
quiet zone. Only `ticket.reference` is passed as the QR value. The printed text
matches that reference exactly. The modal can be closed with Close or Escape.
Print ticket opens the browser's print dialog. Print CSS hides the application
and dialog controls, leaving only the selected ticket and QR, not the dashboard.

To try a code with the webcam, show the selected QR on another screen or print
it, return to Check-in, and select Scan QR code. Review the decoded ticket, then
confirm only when ready to change that demo ticket. QR generation and printing
do not check in a ticket. Codes remain displayable after check-in; the existing
backend still rejects a second check-in with HTTP 409.

### Step 7 verification

`npm.cmd run test:e2e` now runs the existing check-in cases and focused dashboard
cases in a temporary SQLite database. Dashboard tests verify the initial 15
unchecked tickets, an actual check-in and navigation refresh, explicit Refresh,
loading/empty/error states, mobile layout, and print-media isolation. All 15
rendered SVG QR codes are decoded in headless Chrome using the **real**
@zxing/browser image decoder (bypassing the camera test fixture), and each decoded
value must exactly equal its reference. The print button is intercepted and CSS
is tested with print-media emulation; no physical paper or hardware scan is
claimed by these tests. The test harness compares demo rows before and after.

Generated artifacts include dashboard screenshots and selected-ticket-print.png
in the ignored test-results directory. The browser-results JSON records the QR
round-trip reference attachment. No backend source changes are needed.
